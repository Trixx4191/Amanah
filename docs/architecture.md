# Architecture

## Overview

```
File (PDF/DOCX/TXT/MD)
   │
   ▼
agent/ingestion.py    → parses file into (text, page, doc_id) records
   │
   ▼
agent/chunking.py     → splits into overlapping, sentence-aware chunks
   │
   ▼
agent/embeddings.py   → converts chunks to 384-dim vectors (local model)
   │
   ▼
agent/vector_store.py → stores vectors + metadata, persisted to disk
   │
   ▼  (at query time)
agent/reasoning.py    → Thought/Action/Observation loop, calls the
   │                     vector store as a "search_documents" tool
   ▼
agent/llm.py           → local GGUF model via llama.cpp, does the
                          actual language generation

agent/memory.py         → tracks conversation history across turns,
                           summarizing older turns to stay in context

agent/knowledge_base.py → glues ingestion→chunking→embedding→store
                           into add_document()/remove_document()

agent/cli.py             → command-line interface tying it all together
```

## Why each piece works the way it does

**Ingestion is format-specific but produces a uniform output.** Every
parser (`ingest_pdf`, `ingest_docx`, `ingest_text`) returns the same
`IngestResult` shape, so nothing downstream needs to know or care what
file format something came from.

**Chunking splits on meaning, not character count.** We split on
paragraph boundaries first, falling back to sentences only when a
paragraph itself is too long, and only hard-cut as a last resort. This
keeps each chunk coherent, which directly improves retrieval quality —
a chunk that's a fragment of two unrelated sentences embeds poorly.

**The vector store is a from-scratch flat index (numpy), not a
black-box library.** For a knowledge base in the thousands-to-tens-of-
thousands of chunks range, a brute-force cosine similarity scan is
fast enough (numpy's BLAS backend does this in milliseconds) and keeps
the whole system transparent and dependency-light. It supports
deletion by document, which was a hard requirement from day one.

**The reasoning loop is what makes this an agent.** A plain RAG
pipeline does: embed query → retrieve → stuff into prompt → generate.
That's a single-shot lookup with no ability to recognize when the
first search wasn't good enough, or to break a multi-part question
into sub-searches. Our loop instead lets the model reason explicitly
(`Thought:`), decide to search (`Action: search_documents[...]`),
see what came back (`Observation:`), and either search again or
answer (`Final Answer:`). This is the ReAct pattern, implemented here
from scratch rather than via a framework.

**Confidence is checked programmatically, not just by instruction.**
The system prompt tells the model to flag weak answers, but we also
track the similarity scores of what was actually retrieved
(`LOW_CONFIDENCE_THRESHOLD` in `reasoning.py`) and surface that
independently — belt and suspenders, since models don't always follow
instructions perfectly.

**Citations are appended by us, not generated by the model.** We
track exactly which chunks were retrieved and used, then append their
source filename/page directly — this avoids the failure mode where a
model "cites" a plausible-sounding but wrong source.

## What's been tested vs. what needs your machine

Everything except actual language generation has been built and
verified with real tests (`pytest tests/` — 19 passing):
- PDF/TXT ingestion (real files, real text extraction)
- Chunking (paragraph/sentence splitting, overlap, edge cases)
- Vector store (search ranking accuracy, deletion, save/load persistence)
- The full reasoning loop's control flow (parsing Thought/Action/Final
  Answer, multi-step search, max-iteration fallback, citation
  toggle, low-confidence flagging) — tested against a scripted fake
  LLM so the *logic* is verified independent of any specific model

What can only be verified on your machine: actual model loading,
generation quality, and real-world speed — because this development
environment has no GPU/CPU profile matching yours and can't download
model weights. See `docs/setup.md` step 6 for the benchmark script.

## Known limitations / things to revisit

- Chunk size (800 chars) and overlap (150 chars) are reasonable
  defaults, not tuned against your actual documents yet
- The low-confidence threshold (0.35 cosine similarity) is a
  placeholder — worth tuning once you see real retrieval scores on
  your own documents
- Scanned/image-only PDFs aren't supported (no OCR yet) — `ingest_pdf`
  will raise a clear error if it can't extract text
- The vector store is brute-force; fine up to tens of thousands of
  chunks, would need a FAISS swap-in beyond that (the `VectorStore`
  interface is designed so this is a contained change)
